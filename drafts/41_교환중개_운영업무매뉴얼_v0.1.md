## 1. 총칙

### 1-1. 목적
이 매뉴얼은 교환(나목)·중개(마목) 서비스의 관리자 도구(DSRV Admin)와 커스터디 접점에서 운영자가 **언제, 어느 화면에서, 무엇을 확인하고, 무엇을 누르는지**를 정한다.

### 1-2. 적용 범위
- DSRV Admin 2화면: 홈(ADM-02 · 처리함 4섹션 + 데이터 다운로드) · 설정(ADM-03 · 정책값 + 기관 관리)
- 커스터디 접점 3가지: 집행 명세 Excel 전달 · txHash 입력 · 거래 건 상태 변경 통지(웹훅) 수신
- 콜드 서명·전송, 고객확인, BLF·KYT 심사, STR 작성은 이 매뉴얼 밖(Custody-M-01 · Compliance-M-11)

### 1-3. 용어
지침 제3조를 따른다. 화면에서 쓰는 말만 덧붙인다.

| 화면 용어 | 뜻 |
|---|---|
| ① 거래 승인 | 나목(T1)·마목(T2) 건을 콜드 이전으로 넘길지 정하는 섹션 |
| ② 집행 대기 | 콜드 이전 1건 = 1행. 명세 확인·Excel·txHash·완료 |
| ③ AML 판단 | 이상거래 룰(T5) 적중 건 |
| ④ 운영 알림 | N1 시세 · N2 재고 · N3 집행 대사 · X3 3면 대사 · T8 계정 잠금 |
| 행 잠금 | 다른 관리자가 처리 중인 행. 버튼 전부 비활성 · "처리 중 · DSRV-OPS-NN" 표시 |
| 확장 패널 | 행을 클릭하면 아래로 펼쳐지는 상세. 동시 1개 |
| 사유 다이얼로그 | 카테고리 ▾ + 자유입력 10~500자. 보류·거절·이전 중지·STR 검토·무혐의 종결·조치 완료에 공통 |
| 에스컬레이션 | 자동검증 주의 이상. 상태 열에 표시 · 자동 거절 아님 |

### 1-4. 개정 및 관리
- 작성 = 운영 담당 · 검토 = 팀장 · 승인 = 준법감시인(Custody-M-01 1장 4) 준용). ⚠️[확인필요] 관리 부서.
- 스토리보드(ADM-02·03·케이스분기)가 바뀌면 같은 커밋 또는 같은 주에 이 문서의 해당 절을 고친다. 지침 별표 1 값이 바뀌면 이 문서의 `{정책값}` 표기를 일괄 교체한다.

### 1-5. 증적 보존
- 관리자의 모든 처리(승인·보류·거절·이전 중지·검토·STR 이관·무혐의·확인·조치 완료·정책 저장·txHash 입력·Excel/CSV 다운로드)는 시스템 감사로그에 자동으로 남는다. 별도 수기 기록은 **콘솔 밖에서 한 일**에만 필요하다: 계정 잠금 해제 본인확인(2-9) · 슬랙 통보 수신·처리(2-6) · 재고 보충 요청(2-8) · 커스터디 이메일 요청(2-1).
- 콘솔 밖 기록은 ⚠️[확인필요] 양식·저장 위치(팀 문서함)로 남기고 15년 보존한다(지침 제42조).

## 2. 업무 처리 절차

각 절은 같은 틀로 쓴다: **언제** 이 일이 생기는가 → **어디서** → **확인할 것** → **절차** → **결과** → **하지 말 것** → 케이스 ID.

### 2-1. 기관 초대·등록 (ADM-03)

**언제** 커스터디팀이 신규 기관의 오프라인 온보딩(계약·CDD)을 끝내고 customerNo · 수탁 지갑 주소 · 법인명을 이메일로 보내왔을 때. `AC-01`
**어디서** ADM-03 설정 › 기관 관리 › 초대 폼(기관명 · 가입자 이메일 · customerNo · 수탁 지갑 주소).
**확인할 것**
- customerNo 형식 `L-XXXXXX-XXXX` · 수탁 지갑 주소는 커스터디 안내 값을 **그대로**(EIP-55 체크섬은 화면이 검증) · 이미 가입자가 있는 기관이 아닌지(기관당 1명).
- 가입자 이메일이 기관 대표 계정 소유자인지(커스터디 온보딩 서류의 담당자와 일치).
**절차**
1. 4칸 입력 → [초대 발송]. 화면이 형식·중복(기관 간, 운영·재고·에스크로 주소와 중복 불가)을 검사한다.
2. 발송 결과 배너 확인. 초대 링크 유효 `{정책값 72시간}` · 1회용.
3. 기관 목록에 상태 칩 "초대 발송됨"이 생겼는지 확인. 기관 상태 칩은 커스터디 조회값(초기 활성 예상)과 조회 시각이다.
**결과** 가입자가 링크로 ONB-01(비밀번호) → ONB-02(인증 앱) → ONB-03(복구 코드)을 마치면 "활성". `AC-03`
**후속**
- 링크가 만료되면 고객이 관리자에게 재발송을 요청한다 → 기관 행 [초대 재발송]. `AC-02`
- 주소·법인명이 틀렸으면 이 화면에서 못 고친다. **커스터디에 이메일로 정정 요청**하고 요청 일시를 기록한다. 정정 값의 우리 DB 반영 경로는 ⚠️[결정필요](09 §0 (21) D5).
**하지 말 것** 고객이 알려준 주소를 직접 받아 입력하지 않는다(커스터디 안내 값만). 가입자 교체를 위해 초대를 추가로 보내지 않는다(기존 계정 해지 후 재초대).

### 2-2. ① 거래 승인 — T1 나목 교환

**언제** 고객이 EXC-02에서 [수락]을 누르면 ① 섹션에 T1 행이 생긴다. 상태는 "승인 대기" 또는 자동검증 불량 시 "에스컬레이션". `EX-06`
**어디서** ADM-02 › ① 거래 승인 › T1 행 → 클릭해 확장 패널.
**확인할 것(확장 패널 순서대로)**
1. **건**: 요청번호(EXC-YYYYMMDD-NNNN) · 기관 · 수락 시각
2. **교환**: 보내는 수량 → 받는 수량 · 확정 비율 · 스프레드 · 원화 환산액
3. **예상 가스비**: 참고값. 실수령 예상액이 EXC-02 고지값과 같은지
4. **자동검증 칩 6개**: 건별 한도 ≤ `{정책값 1,500,000원 상당}` · 교환 재고 충족 · 기관 상태 02 활성 · BLF · KYT · 이상거래 룰. **황색·적색 칩이 있어도 시스템은 거절하지 않는다. 그 판단이 이 절차다.**
5. **이전 계획**: 입고(고객 수탁 → 교환 재고) · 출고(교환 재고 → 고객 수탁 · 가스 차감 후) 2건
6. **처리 이력**: 에스컬레이션 사유 · 연계 ③ 건 유무("③ 1건" 표시)
**절차 — 셋 중 하나**
- **[승인]**: 활성 조건 = 상태가 승인 대기·에스컬레이션·보류 / 행 잠금 없음 / 교환 재고 ≥ 받는 수량 / 기관 상태 02 활성(**클릭 시 커스터디 조회**). 확인 다이얼로그에서 수량·비율·실수령 예상액을 다시 읽고 [승인]. → 행이 사라지고 ②에 입고·출고 2행이 생긴다. 고객 화면 변화·통지 없음(EXC-03 '진행 중' 유지). `EX-09`
- **[보류]**: 사유 다이얼로그(카테고리: 자동검증 재확인 / 트래블룰 정보 미비 / 서류 보완 요청 / 기타 + 10자 이상). 행은 남고 상태 '보류'. **만료 시한이 없다** — 반드시 [승인] 또는 [거절]로 닫는다. 고객 화면 변화 없음. `EX-08`
- **[거절]**: 사유 다이얼로그(카테고리: 자동검증 부적합 / AML 사유 / 기타). 비가역. → 행 제거 · 잠긴 수량 해제 · 고객 EXC-04 「거절 (DSRV 심사)」+ "내부 심사 기준에 따라 거절되었습니다" · 이메일 ⑤. 카테고리가 **AML 사유**면 ③에 검토 건이 자동 생성된다. `EX-10`
**연계 ③ 건이 있을 때** 먼저 ③ 섹션에서 그 건을 본다(2-7). STR 검토로 넘길 거면 이 ① 건은 통상 거절한다 ⚠️[확인필요: 연계 처리 규칙]. 무혐의 종결하면 이 행의 에스컬레이션 표시가 풀린다.
**실패 시** "이미 처리된 건입니다" 배너 = 다른 관리자가 먼저 처리(목록 자동 갱신). 재고 부족 인라인 ⚠ = 재고 보충 후 다시(2-8 N2). 서버 오류 배너 = 잠시 후 재시도.
**하지 말 것** 자동검증이 전부 녹색이라고 확인 없이 승인하지 않는다(가스비·실수령 예상액 대조는 사람만 한다). 거절 사유에 STR·심사 내용을 쓰더라도 고객 문구는 시스템이 일반화하므로 사유란에는 내부용으로 정확히 쓴다. 보류를 오래 두지 않는다(월 점검 대상).

### 2-3. ① 거래 승인 — T2 마목 확정

**언제** 게시자가 BRK-04에서 [수락]을 누르면 거래가 **확정**되고 ①에 T2 행이 생긴다(확인 대기 / 에스컬레이션). 확정 전(게재중·협의중)에는 어드민에 아무 행도 생기지 않는다. `ST-01`
**어디서** ADM-02 › ① 거래 승인 › T2 행 → 확장 패널.
**확인할 것**
1. **건**: 거래번호(BRK-YYYYMMDD-NNNN) · 게시자 ↔ 신청자 · 수락 시각
2. **교환**: 게시자 보내는 수량 / 신청자 보내는 수량 · 비율 · 양측 원화 환산
3. **수수료**: 각자 보내는 수량의 `{정책값 1.00%}` · **예치 수량에 포함**되어 들어간다
4. **예상 가스비**: 양측 각 예치 1 + 인도 1 = 2회분 · 인도 수량에서 차감
5. **자동검증**: 양측 한도 · 양측 잔고(**수수료 포함**) · 양측 기관 상태 · BLF 양측 · KYT 양측 · 이상거래 룰
6. **이전 계획**: 예치 2건(각자 수탁 → 에스크로 · 거래 수량 + 수수료). 양건 완료 시 인도 2건 자동 생성
**여기서 정하는 것** 거래 성립 여부가 아니다. 이미 확정된 거래의 **에스크로 예치를 시작해도 되는가**다.
**절차 — 셋 중 하나**
- **[승인]**: 활성 조건 = 확인 대기·에스컬레이션·보류 / 행 잠금 없음 / 양측 잔고(수수료 포함) 확보 / 양측 기관 02 활성(클릭 시 조회). 확인 다이얼로그 → [승인]. → 행 제거 · ②에 예치 2행 · 고객 BRK-05 스텝 2 '예치 진행'. `ST-03`
- **[보류]**: 2-2와 같다. 고객 BRK-05에 "이전 보류" 배너(문구 ⚠️[결정필요]). `ST-02`
- **[이전 중지]**: 사유 다이얼로그 · 비가역. 예치 전이므로 자산 이동 없음 · 수수료 없음 · 양측 BRK-05 이전 중지 배너 · 통지 ⚠️[확인필요]. `ST-04`
**실패 시** 잔고 재검증 실패 = 확정 후 잔고가 줄었음 → 행은 보류로 남고 인라인 ⚠ "확정 후 잔고가 부족해졌습니다 — 보완 후 승인해 주세요". 고객에게 보완을 안내할 채널 ⚠️[확인필요].
**하지 말 것** 마목에는 [거절]이 없다. 확정된 거래를 무산시키는 것은 [이전 중지]이고, 그 계약상 귀결은 ⚠️[로펌게이트](지침 제25조④)이므로 사유를 특히 정확히 남긴다.

### 2-4. ② 집행 대기 — 명세 확인 · Excel 전달 · txHash · 완료

**언제** ①에서 승인하면(나목 입고·출고 2행 / 마목 예치 2행), 양건 예치가 끝나면(인도 2행 자동), 예치 후 중지하면(반환 행), 정책 주기가 오면(수수료 스윕 행). 행 하나 = 콜드 이전 1건. `EX-09 · ST-03 · ST-07 · ST-06 · ST-09`
**어디서** ADM-02 › ② 집행 대기 › 행 → 확장 패널(= 집행 명세).
**역할 분담**

| 단계 | 누가 | 어디서 |
|---|---|---|
| a. 명세 확인 · [명세 Excel] 다운로드 | 운영 관리자 | ADM-02 ② |
| b. Excel 전달 · 품의 · 집행 전 심사(BLF·KYT) · 콜드 2인 서명 · 전송 | 커스터디팀 | 콘솔 밖(Custody-M-01) |
| c. 심사에서 문제가 있으면 거래 건 상태 변경 통지(웹훅) | 커스터디 | → 2-6 |
| d. txHash 입력 | 커스터디 담당자(어드민 계정) | ADM-02 ② |
| e. 온체인 대사 → [완료] | 시스템 판정 · 운영 관리자 클릭 | ADM-02 ② |

**절차**
1. **명세 확인(a)**: 확장 패널에서 건 · 출금 지갑 · 수신 주소(전문·소문자) · 자산·수량 · 명세 해시 · 승인자 · 다음 단계를 읽는다. 수신 주소가 자산 묶음 4개 중 어느 지갑인지 라벨로 확인한다(교환 재고 RSV-01 / 에스크로 전용지갑 / 고객 수탁).
2. **[명세 Excel]**: 1건 1파일 동기 생성. 열 = 행 ID · 유형 · from · to · 자산 · 수량 · 요청 기관 customerNo·법인명 · 승인자 · 승인 시각 · 만료 시각 · 요청 시점 KRW 환산 · 명세 해시(최종 열 구성은 커스터디 합의 ⚠️[확인필요]). 다운로드는 열람 기록에 남는다. **다운로드하지 않아도 완료는 막히지 않는다** — 완료를 막는 것은 대사 불일치 하나다.
3. **커스터디 전달(b)**: 파일을 커스터디팀에 넘긴다. 전달 경로(별도 채널 / 시스템 연동)는 ⚠️[확인필요]. 정산 배치 `{정책값 1영업일 3회}`에 맞춘다(배치 시각 ⚠️[확인필요]).
4. **순서 지키기**: 나목 **출고는 입고 완료 후에만 활성**된다(입력창에 "입고 완료 후" 안내). 마목 인도는 예치 2건이 모두 완료된 뒤 자동으로 생긴다. 한쪽 예치만 끝난 상태에서 인도를 만들 방법은 없다.
5. **txHash 입력(d)**: `0x` + 16진수 64자. 포커스 아웃 또는 Enter → 시스템이 온체인에서 **발신 지갑 · 수신 주소 · 자산 · 수량** 4항목을 명세와 대조한다. 전부 일치 → 녹색 "명세 일치" + [완료] 활성.
6. **[완료](e)**: 확인 없이 즉시. 행 제거 · 후속 행 활성/자동 생성 · 거래의 마지막 행이면 고객 화면 '완료' + 이메일 ③ · 실발생 가스비를 영수증 값으로 기록. `EX-11 · EX-12 · ST-05 · ST-08`
**대사 불일치일 때** [완료] 비활성 · 어긋난 항목 빨간 칩 · ④에 N3 알림 생성 · 행 정지 · 후속 자동 생성 정지. → 2-8 N3. **명세를 고치지 않는다.** `EX-13 · ST-10`
**행 유형별 메모**

| 유형 | 특기 |
|---|---|
| 입고(나목) | 차감 없음 · 고객이 보내는 수량 그대로 |
| 출고(나목) | 이체 수량 = 받는 수량 − 예상 가스비. 실발생 가스비와 차이는 회계에서 정리. **실패 종결 없음** |
| 예치(마목) ×2 | 이체 수량 = 거래 수량 + 수수료. [보류]·[이전 중지] 버튼이 이 행에 있다(2-5) |
| 인도(마목) ×2 | 이체 수량 = 상대 거래 수량 − 가스비. 별도 승인 없이 자동 생성됐지만 서명은 사람 |
| 반환(마목) | 에스크로 → 예치자 · 수수료 없음 · 가스비 부담 ⚠️[확인필요] |
| 수수료 스윕 | 에스크로 → 운영 · 자산별 1행 · 주기 ⚠️[확인필요] |

**하지 말 것** 커스터디 중지 통지가 온 거래의 행은 사라진다 — 없는 행에 txHash를 입력하려 하지 않는다(온체인에 이미 보냈다면 2-6 ③). 대사 불일치를 "수량이 비슷하니" 넘기지 않는다(완전 일치만 통과).

### 2-5. ② 예치 후 보류 · 이전 중지 · 반환

**언제** T2를 승인한 뒤(① 행이 사라진 뒤) 그 거래를 멈춰야 할 때. 예치·인도 행에만 [보류]·[이전 중지]가 있다. `ST-06`
**절차**
- **[보류]**(가역): 사유 다이얼로그. 그 거래의 미집행 행을 정지시키고 사유를 남긴다. 재개는 같은 행에서. 만료 없음. 예치분은 에스크로에 잠긴 채다.
- **[이전 중지]**(비가역): 사유 다이얼로그. 미집행 행 전부 제거 → 이미 예치된 건수만큼(1 또는 2) **반환 행** 생성(에스크로 → 예치자 수탁 · 수수료 없음) → 양측 BRK-05 이전 중지 배너 + 반환 안내. 반환 행은 2-4 절차로 집행·완료한다.
**확인할 것** 어느 예치가 완료(txHash 대사 완료)됐는지 — 반환은 완료된 예치에만 생긴다. 예치가 온체인에 이미 전송됐는데 txHash가 아직 입력 전이면, 먼저 txHash를 입력·완료한 뒤 중지한다(그래야 반환 행이 생긴다).
**하지 말 것** 반환 완료 후 에스크로에 그 거래 잔여가 남으면 안 된다(3면 대사에서 잡힘). 반환 이전의 가스비 처리는 ⚠️[확인필요]이므로 발생 시 기록해 둔다.

### 2-6. 커스터디 거래 건 상태 변경 통지(웹훅) · 통지 실패 시 슬랙 절차

**언제** 커스터디가 집행 전 심사(BLF·KYT 등)에서 특정 거래 건의 상태를 바꾸면 웹훅이 온다. 내용 = 거래 건 번호(EXC-/BRK-) + 상태값(**중지** / **해제**). 사유·단계는 오지 않는다. `케이스분기 §4 규칙 · ADM-02 ② '커스터디 차단' 열`
**시스템이 자동으로 하는 것(관리자 조치 없음)**

| 수신 | 자동 처리 | 관리자가 볼 곳 |
|---|---|---|
| 중지 | 그 거래의 미집행 ② 행 전부 거절 → 거래 거절 → 마목에서 예치 완료 다리가 있으면 **반환 행 생성** → 고객 "이슈로 진행 불가" 배너 · 이메일 ⑤ | ② '커스터디 차단' 열에 수신 시각 · 반환 행 · 감사로그 |
| 해제 | **수신 시각 기록만.** 거절된 행·거래를 되살리지 않는다. 고객이 다시 요청한다 | ② '커스터디 차단' 열 · CSV ② |
| 종결된 건에 재통지 | 기록만 | 감사로그 |

**관리자 절차**
1. 중지 수신으로 반환 행이 생겼으면 2-4로 집행·완료한다.
2. 고객이 "왜 진행 불가냐"고 물으면 4-9의 문구로만 답한다. 심사 내용은 우리도 받지 않았고, 받았더라도 말하지 않는다.
3. 해제 통지에 따라 거래를 재개해 달라는 요청은 거절한다. 고객이 새로 요청·게시하도록 안내한다.
**통지 실패 시(슬랙 절차 — 내부 운영 규칙 · 커스터디 요청 항목 아님)** `09 §0 (22)④`
1. 커스터디가 웹훅 재시도까지 실패하면 **슬랙 채널** ⚠️[확인필요: 채널명]로 거래 건 번호와 상태값을 알린다.
2. 슬랙 확인 담당은 운영 관리자 당번 ⚠️[확인필요: 당번·확인 시한(예: 영업시간 내 1시간)].
3. 상태값이 **중지**면 → ADM-02 ② 해당 거래의 행에서 **[이전 중지]**(사유 카테고리 'AML 사유' · 자유입력에 "커스터디 슬랙 통보 {일시} 수신")로 수동 처리한다. 예치 완료분이 있으면 반환 행이 생긴다. 고객 안내는 시스템이 한다.
4. 상태값이 **해제**면 → 아무 것도 하지 않고 슬랙 스레드에 "확인 · 조치 없음"을 남긴다.
5. 슬랙 수신·처리는 콘솔 밖 기록(1-5)에 남긴다: 수신 일시 · 거래 건 번호 · 상태값 · 처리자 · 처리 일시.
6. 되묻는 조회 API는 없다. 통지가 안 온 미집행 행은 집행 대기에 그대로 남으므로(보류 만료 없음), **일 마감 시 ② 행 중 오래 머무는 것**을 슬랙 누락 후보로 점검한다(3-1).
**하지 말 것** 웹훅 중지 통지 후 온체인에 이미 전송된 예치가 있다면 그 tx는 되돌릴 수 없다. txHash를 입력·완료해 장부를 맞춘 뒤 반환 행으로 돌린다(반환 행은 대사 완료된 예치에만 생긴다).

### 2-7. ③ AML 판단 — 이상거래 룰 적중(T5)

**언제** 이상거래 룰(자전 · 통정 · 위장게시 · 비정상 교환 패턴)이 적중하면 ③에 T5 행이 생긴다. ①에서 'AML 사유'로 거절했을 때와 T8 잠금 유지·이관 때도 생긴다. `AM-01 · AM-05`
**어디서** ADM-02 › ③ AML 판단 › 행 → 확장 패널(룰 · 대상 · 타임라인 · 연계 ① 건 · 업무 상태).
**절차**
1. **[검토]**: 확인 없이 즉시. 상태 '검토중' · 담당자·착수 시각 기록. 검토 담당자 잠금 ⚠️[확인필요].
2. 룰 내용·타임라인·연계 거래를 본다. 필요하면 CSV ②(거래 요청 목록)·③(콜드 이전 목록)로 같은 기관의 이력을 뽑는다.
3. **[STR 검토]**(비가역): 사유 다이얼로그 → 별도 AML 시스템으로 이관. 고객 통지·화면 표시 없음. 기관 단위 제한이 필요하면 커스터디에 통보한다(우리는 기관 상태를 바꾸지 않는다). 연계 ① 건은 통상 거절 ⚠️[확인필요]. `AM-03`
4. **[무혐의 종결]**(비가역): 사유 **필수**(감사 대상). 연계 ① 건의 에스컬레이션 표시가 풀린다. `AM-04`
**하지 말 것** 고객 화면·이메일·유선 어디에도 이 섹션의 존재를 드러내지 않는다(누설 금지 · 지침 제8조 5호). ①에서 연계 건을 거절할 때 사유 카테고리는 'AML 사유'로 하되 고객에게는 시스템 일반화 문구만 나간다.

### 2-8. ④ 운영 알림 — N1 시세 · N2 재고 · N3 집행 대사 · X3 3면 대사

**공통** 실제 조치는 화면 밖에서 하고, 어드민에서는 **[확인]**(봤다는 기록 · 이후 [조치 완료] 활성) → **[조치 완료]**(결과 ▾ 선택 + 사유 · 비가역)만 한다. `OP-01~04`

| 유형 | 언제 | 시스템 자동 | 화면 밖 조치 | [조치 완료] 결과 |
|---|---|---|---|---|
| **N1 시세 소스 수신 중단** | 무수신 임계(⚠️미정) 경과 | 신규 요청·게시·신청 차단 · price guard 판정 정지 · 진행 중 건 영향 없음 | 소스 상태 확인 · 복구 대기. **대체 소스로 바꾸지 않는다** | 정상 수신 확인 → 차단 해제 |
| **N2 교환 재고 부족** | 수락 시 재검증에서 재고 부족 만료 발생 | 해당 요청 만료 · 가용 재고 0이면 [거래 요청] 비활성 | 운영 지갑 → 교환 재고 지갑 콜드 이전을 커스터디에 요청(Custody-M-01 절차 · ②에 행이 생기지 않는 별도 이전 ⚠️[확인필요]) · ADM-03 자산풀 수량이 자동 반영될 때까지 대기 | 재고 보충 확인 |
| **N3 집행 대사 불일치** | ② txHash 4항목 중 하나라도 명세와 다름 | [완료] 차단 · 행 정지 · 후속 자동 생성 정지 · 고객 '진행 중' 유지(알리지 않음) | 원인 규명. 수량 차이면 **차액 회수 이전을 ②에 새로 만들어 집행**한 뒤 재대사. 명세는 고치지 않는다. 주체·순서 ⚠️[확인필요] | 정정 완료 · 재대사 → ② 행 재활성 |
| **X3 3면 대사 불일치** | 일일 대사 배치에서 내부 장부·온체인·커스터디 콜드 기록 세 값이 어긋남(자산 묶음 4개 전부 대상) | 해당 지갑 신규 이전 정지(범위 ⚠️[확인필요]) | ②③이 같고 ①만 다르면 우리 장부 오류 → 가스비 전기 누락·집행 미반영부터 본다. ①②가 같고 ③만 다르면 커스터디 기록 확인 | 일치 확인 — **최신 배치가 일치일 때만 활성** |

**하지 말 것** N1에서 차단을 풀기 위해 소스를 임의로 바꾸지 않는다. X3를 불일치 상태에서 닫을 방법은 없으니 원인을 찾는다.

### 2-9. ④ 계정 잠금(T8) — 해제 · 잠금 유지·이관

**언제** 가입자의 로그인 실패(비밀번호·인증 코드·복구 코드 합산)가 `{정책값 5회}`에 이르면 계정이 잠기고 ④에 T8 행이 생긴다. `AC-04`
**절차**
1. **[확인]**.
2. **콘솔 밖 본인확인**: 등록 연락처(유선)로 기관 담당자 확인 + 초대 이메일 소유 확인. 확인 기록(확인자 ID · 일시 · 방법)은 **필수**이며 콘솔 밖 기록(1-5)에 남긴다.
3. 본인이고 단순 실수면 **[조치 완료 → 해제]**: 활성 복귀 · 실패 카운트 0 · 기존 비밀번호·OTP로 로그인. `AC-05`
4. 탈취 의심이면 **[조치 완료 → 잠금 유지·이관]** + 사유: 잠금 유지 · ③에 검토 건 생성 · 그 기관의 ①·② 대기 건 **일괄 거절**(예치 완료분은 반환 행) · **커스터디에 통보**해 기관 상태 판단을 맡긴다(우리는 기관 상태를 바꾸지 않는다). 고객에게 통지하지 않는다(누설 금지). `AC-06 · AC-08`
**하지 말 것** 본인확인 기록 없이 해제하지 않는다. 가입자 개인 연락처가 아닌 **기관 등록 연락처**로 확인한다.

### 2-10. 기관 상태 비활성 확인 시 (시스템 자동 · 관리자는 결과 확인)

**언제** 관문 조회(로그인 · 요청/게시/신청 · 수락/확정/① [승인] 클릭 · ADM-03 진입)에서 customerStatusCd가 02 활성 외(01·03·04·05·06)로 확인된 순간. 변경 웹훅은 없으므로 **다음 관문에서 잡힌다**. `AC-07 · AC-08 · AC-09`
**시스템 자동** 그 기관의 ① 대기 건 전부 거절 · ② 미집행 행 취소 · 예치 완료분 반환 행 · 집행 중 이전은 대사 후 정지 · 고객 배너 + 이메일 ⑤(일반화 사유).
**관리자 절차**
1. ADM-03 기관 목록에서 상태 칩(코드 + 조회 시각)을 확인한다. 상태별 문구 차등은 없다.
2. 반환 행이 생겼으면 2-4로 집행·완료한다.
3. 05 거래해지 기관: 해지 절차·잔고 반환은 커스터디가 한다. 이 서비스에 해지 흐름은 없다. 새 초대는 커스터디의 해지·재등록 확인 후 ⚠️[확인필요].
4. 고객 문의는 "기관 상태 관련 사항은 커스터디 담당자에게 확인해 주세요"로 안내한다(사유는 우리도 받지 않는다).
**하지 말 것** ADM-03에서 기관 상태를 바꾸려 하지 않는다(버튼이 없다). 압류·동결·재이행 미완 등 사유를 고객에게 추측해 말하지 않는다.

### 2-11. 설정 변경 (ADM-03) — 정책값 · 취급 자산 중지

**정책값 저장** `지침 제41조 · 별표 1`
1. 변경 전 준법감시인 검토·승인 문서(⚠️[확인필요] 양식)를 받는다. 한도·수수료율은 약관·고객 고지 개정을 병행한다.
2. ADM-03에서 값 입력(단위는 칸 밖 표시) → 바뀐 셀 ● 표시 → **[변경 저장]**(2인 승인 없음 · 확인 다이얼로그 없음). 정책 버전 +1 · 토스트 "정책값이 저장되었습니다 (vN) — 신규 요청부터 적용".
3. 같은 날 지침 별표 1을 개정하고 이 매뉴얼의 `{정책값}` 표기를 교체한다.
4. 진행 중 건은 생성 시점 값을 유지한다. 고객이 "왜 내 건은 옛 값이냐"고 물으면 이 규칙을 안내한다.
**취급 자산 중지** `지침 제9조③`
1. 자산 행 드롭다운 ▾ → '중지' → 확인 다이얼로그 + 사유(필수) → 즉시 적용. 그 자산이 든 페어 2종의 신규 요청·게시·신청 차단 · 진행 중 건 유지. 게재중 게시의 자동 중지 여부 ⚠️[확인필요].
2. 자산의 영구 제외·신규 추가는 이 화면으로 하지 않는다(변경신고 사안 · 거래지원 지침).
3. '활성' 복귀는 확인 없이 즉시.
**하지 말 것** 시세 소스는 이 화면에서 고를 수 없다(2026-09-04 삭제). 재고 수량은 표시 전용 — 수기 보정 기능이 없다.

### 2-12. 데이터 다운로드 · 열람

- ADM-02 하단 CSV 6종: ① 기관·가입자 ② 거래 요청 ③ 콜드 이전 ④ 구분회계 ⑤ 3면 대사 ⑥ 열람 기록. 기간·조건 선택 없음(전체 기간 스냅숏 · 동기 생성).
- **모든 다운로드는 ⑥ 열람 기록에 남는다.** 업무 목적 없이 내려받지 않는다.
- 개인식별정보는 CSV에서도 마스킹되어 있다. 마스킹 해제본을 요구받으면 준법감시인 승인 없이 제공하지 않는다.
- 구분회계 계정명(스프레드수익 · 중개수수료 · 가스비 비용/회수)은 CSV ④에만 있다. 고객에게 계정명을 언급하지 않는다.
- 어드민 화면에는 건수 집계가 없다. 건수가 필요하면 CSV로 센다.

### 2-13. 업무 종료 시 (일 마감)

1. ADM-02를 새로고침해 4섹션을 한 번 순회한다(자동 갱신이 없다).
2. ① 보류 행 · ② 정지 행 · ③ 검토중 행 · ④ 확인만 된 행에 **오늘 진전이 없으면** 사유·다음 조치를 콘솔 밖 기록에 남긴다.
3. ② 행 중 예치·인도가 오래 머무는 건은 커스터디 슬랙 누락 후보(2-6 통지 실패 6)) 또는 배치 지연이다 — 커스터디에 확인.
4. 확장 중인 행과 저장하지 않은 txHash 입력은 화면 이동 시 확인 없이 버려진다. 입력 중이면 마치고 나간다.
5. 관리자 배지 › 로그아웃(세션 즉시 파기).

## 4. 업무 이슈 발생 및 해결

"~인 경우"마다 조치 · 고객 안내 문구 · 참조. 고객 안내는 **별첨 1의 문구만** 쓴다.

**4-1. 고객이 "거래 요청 버튼이 안 눌린다"고 할 때** `EX-02 · PB-02`
- 원인 4가지 중 하나: 시세 소스 중단(④ N1 있음) / 교환 재고 부족(ADM-03 자산풀) / 기관 상태 비활성(ADM-03 칩) / 처분 가능 잔고 부족(고객 잔고). 요청 레코드는 만들어지지 않는다.
- 안내: 시세·재고는 "현재 신규 요청을 받을 수 없습니다. 잠시 후 다시 시도해 주세요". 기관 상태는 2-10 ④. 잔고는 고객이 화면에서 본다.

**4-2. 고객이 수락했는데 '만료'가 됐다고 할 때** `EX-05 · EX-07`
- 카운트다운 `{정책값 120초}` 초과, 또는 수락 시 재검증 실패(요청~수락 사이 재고 소진 · 비율 이탈). 새로 요청하면 된다. 재고 부족이면 ④ N2가 생겼을 것이다.

**4-3. 마목 T2 승인 시 "확정 후 잔고가 부족해졌습니다"** `ST-02`
- 확정 후 그 고객의 수탁 지갑 잔고가 줄었다(다른 거래 예약 등). 행은 보류. 고객에게 보완 안내 ⚠️[확인필요: 채널·문구]. 보완이 안 되면 [이전 중지].

**4-4. txHash를 입력했는데 대사 불일치** `EX-13 · ST-10 · OP-03`
- 2-8 N3. 명세를 고치지 않는다. 수량 초과 전송이면 차액 회수 이전, 부족이면 추가 이전을 ②에 만들어 재대사 ⚠️[확인필요: 절차 주체]. 고객 화면은 '진행 중' 그대로이고 정지 사실을 알리지 않는다.

**4-5. 예치가 한쪽만 끝났는데 상대 기관이 비활성이 됐다** `AC-08 · ST-06`
- 시스템이 ① 없음·② 미집행 행 취소·완료된 예치 1건에 반환 행 생성. 반환 행을 2-4로 집행한다. 양측 BRK-05 이전 중지 배너.

**4-6. 커스터디 '해제' 통지가 왔는데 고객이 거래를 다시 열어 달라고 한다** `2-6`
- 열어주지 않는다. "해당 거래는 종결되었습니다. 필요하시면 새로 요청(게시)해 주세요."

**4-7. 계정 잠금 해제 요청** `AC-05`
- 2-9. 본인확인 기록 없이 해제하지 않는다.

**4-8. 초대 링크 만료 · 초대 메일 미수신** `AC-02`
- ADM-03 [초대 재발송]. 이메일 오기면 기존 초대 계정 해지 후 재초대 ⚠️[확인필요: 해지 절차].

**4-9. 고객이 거절·진행 불가 사유를 묻는다** `EX-10 · 2-6`
- "내부 심사 기준에 따라 거절되었습니다" / "이슈로 진행이 불가합니다" 이상은 말하지 않는다. 심사 내용·AML·STR·커스터디 판정을 언급하지 않는다. 기관 상태 관련이면 커스터디 담당자로 안내.

**4-10. 고객이 실수령액이 예상과 다르다고 한다** `EX-12 · ST-08`
- 예상 가스비는 참고값, 실제 차감액은 실발생 가스비다(EXC-02·BRK-04에 고지됨). 예상액을 상한으로 두지 않는다. CSV ③에서 예상·실발생 두 값을 확인해 답한다.

**4-11. 다른 관리자가 처리 중이라 버튼이 잠겼다**
- 행 잠금. 그 관리자와 확인 후 진행. "이미 처리된 건입니다" 배너가 뜨면 목록이 갱신된 것이다.

**4-12. 취급 자산을 중지했는데 게재중 게시가 남아 있다** `2-11`
- 자동 중지 여부 ⚠️[확인필요]. 확정 전 게시는 게시자가 [게시 중단]할 수 있으므로 필요하면 고객에게 요청.

**4-13. 05 거래해지 기관 가입자가 로그인을 시도한다** `AC-09`
- 현재 안 = 조회만 허용. 확정 전 ⚠️[확인필요]. 해지·잔고 반환은 커스터디.

**4-14. customerNo·수탁 지갑 주소를 잘못 입력해 초대를 보냈다** `2-1`
- 이 화면에 수정 기능이 없다. 커스터디에 이메일로 정정 요청 · 반영 경로 ⚠️[결정필요 D5]. 잘못된 주소로 집행 명세가 만들어지지 않도록 그 기관의 거래는 정정 전까지 [보류].

**4-15. 시세 소스 중단이 길어진다** `OP-01`
- 차단을 유지한다. 대체 소스로 바꾸지 않는다. 고객 안내는 4-1 문구. 장기화 시 5장 위기 등급 판정.

**4-16. 3면 대사에서 에스크로만 불일치** `OP-04`
- 인도 완료 후 남는 수수료·가스 차감분이 장부에 회사 귀속으로 나뉘어 있는지 먼저 본다(지침 제31조②). 스윕 행 미집행분도 확인.

## 5. 위기 대응 및 비상상황 관리

### 5-1. 준용
사고·위기의 등급(심각·경계·주의·관심) 판정, 초동 대응, 비상 전파, 금융당국 보고는 **Custody-M-01 5장** 및 **Custody-M-07**을 그대로 따른다. 이 서비스는 핫월렛이 없으므로 핫월렛 시나리오는 해당 없음.
