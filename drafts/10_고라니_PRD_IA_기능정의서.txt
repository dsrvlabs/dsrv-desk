서비스 네이밍 — 왜 ‘고라니’인가
‘고라니’는 한국의 가상자산 규제 환경을 빗댄 이름이다.
한국의 규제는 다른 나라에 비해 유독 심하다.
고라니 역시 전 세계에서 유독 한국에 대다수가 분포한다.
고라니는 어디서 나타날지 예측하기 어렵다 — 한국의 규제도 꼭 그렇다.
예측 불가능하게 출몰하는 규제에 대응한다. 그래서, 고라니다.

1. 돌핀(Dolfin) 벤치마크 — 거래 / 중개 / 통합 자산관리
돌핀(웨이브릿지)은 “법인·고액자산가용 가상자산 관리 플랫폼”으로, 우리가 참고할 3개 축은 다음과 같습니다.
1-1. 거래 (Trading)
검증된 서비스 공급자(국가별 라이선스 보유 LP)로 구성된 유동성 풀을 통해 매매 체결.
거래상대방의 자금세탁 등 법률 리스크로부터 고객을 보호하는 구조(VASP가 중간에서 차단).
금융권 출신 트레이딩 팀의 리스크 관리 시스템 강조.
1-2. 중개 (Brokerage)
블록딜 중개: 거래소에서 소화하기 어려운 대형 주문을 OTC로 처리해 시장 충격(슬리피지) 방지.
트레이딩 플랜: 전문 브로커가 최적 거래상대방을 탐색해 고객별 매매 계획을 설계·제안.
검증 고객 네트워크: 온보딩 시 KYC·자금소명이 사전 완료된 회원 간에만 거래.
사실상 사람(브로커) 중심의 화이트글러브 + 텔레그램 상담 채널.
1-3. 통합 자산관리 (Integrated Asset Management)
맞춤형 트레이딩: 고객 상황별 매매 계획 커스터마이징.
통합 리포팅: 거래 진척 실시간 모니터링 + 결과 리포트 제공.
증명서 발급: 잔고증명, 거래내역 증빙 등 법인 업무용 서류.
1-4. 공통 통제 (우리가 그대로 따라가야 할 부분)
KYC(고객확인) · Travel Rule(송금정보 기록) · STR(의심거래보고) · ISMS · VASP 라이선스.
시사점: 돌핀의 거래·중개는 “완전 자동 매칭 엔진”이 아니라 브로커(사람) + 검증된 유동성 + 수탁의 조합입니다. 고라니 MVP도 동일하게 사람이 개입하는 OTC 데스크 + 얇은 소프트웨어 레이어로 시작하는 것이 심사까지 가장 빠릅니다.

2. 사용자 · 권한 모델
2-1. 가입 / 온보딩
초대 기반 ORG 가입: 운영자(고라니) 또는 ORG 관리자가 이메일 초대 → 가입. 공개 셀프 가입 없음.
법인 KYC는 수기(오프라인) 처리 — 서류 제출·검토는 시스템 밖. 시스템은 KYC 승인 상태만 관리하며, 승인 전까지 거래·출금 제한(조회만 가능).
ORG 단위로 자산·지갑·멤버·승인라인이 격리.

3. 기능 요구사항 (모듈별)
각 모듈에 [개발]/[서드파티]/[사내] 와 (BE/FE/Contract) 를 함께 표기.
A. 인증·계정 — [개발] (BE/FE)
초대 기반 ORG 가입, 로그인, 세션 관리(타임아웃·동시세션 통제).
2FA: TOTP(Google/MS Authenticator) — 표준 라이브러리로 자체 구현 가능. 고도화 필요 시 Auth0 등 [서드파티].
B. 권한관리 (RBAC) — [개발] (BE/FE)
역할·정책·리소스 매트릭스. 관리자/사용자 분리.
C. Policy Engine — [개발] (BE) ★핵심
룰 기반 엔진: 주요 이벤트(출금/이전, 거래 체결, 중개 체결, 임계 금액 초과 등)에 대해 사전 정의된 룰을 평가.
평가 결과에 따라 자동 통과 / 승인라인 라우팅 / 차단 결정.
룰 예시: “출금 ≥ N USDT → 2인 승인”, “신규 출금주소 → 24h 홀드 + OFAC 통과 필수”, “야간 거래 차단”.
※ 커스터디 서명 정책과 2단 구조: 고라니 Policy Engine = 비즈니스 룰/승인 라우팅, 커스터디 정책 = 최종 서명 직전 가드레일.
D. 승인 라인 (Approval Workflow) — [개발] (BE/FE)
Policy Engine 통과 후 특정 이벤트에 대해 N-of-M 순차/병렬 승인.
승인 대기함(Inbox), 승인/반려 사유, 전체 이력 감사.
E. 수탁 지갑 (Custodial Wallet) — [개발 오케스트레이션 + 사내 커스터디] (BE) ★구조 핵심
지갑은 2단 구조 — 운영 핫월렛 + 보관 콜드월렛. 콜드월렛(커스터디)을 운영에 직접 쓰지 않습니다.
운영 핫월렛(수탁 기관 명의): 입금 수령·출금·거래/중개 정산을 집행하는 운영 지갑. 경제적 가치 기준 핫 비중 ≤20% 한도 내 운용.
콜드월렛(사내 커스터디): 보관의무(이용자보호법 ≥80% / ISMS·특금 ≥70% 경제적 가치) 충족 전용 볼트. 키·콜드 보관은 사내 커스터디 책임.
자금 흐름: ORG별 입금주소(HD/MPC 파생) 수령 → 운영 핫월렛으로 스윕 → 초과분 콜드로 이동 / 출금·정산은 핫월렛에서 집행, 잔액 부족 시 콜드 → 핫 보충(커스터디 승인 절차).
고라니 개발 범위: 핫월렛 입출금 오케스트레이션, 입금 감지, 핫↔콜드 스윕 트리거, 핫/콜드 비율 모니터링·알림. (콜드 보관·키관리·최종 서명은 커스터디.)
✅ 선결 과제(커스터디 팀 확인): (a) 주소 발급·서명 API, (b) 운영 핫월렛 서명도 커스터디가 처리하는지(핫 정책 vs 콜드 정책), (c) 콜드 스윕/보충 절차·소요시간, (d) ETH/USDT/USDC·이더리움 메인넷 지원, (e) ERC-20 출금 가스(ETH) 충전 주체.
F. KYC — [수기(오프라인) 전제] (시스템: 상태 플래그만)
전제: 법인 KYC의 서류 제출·검토·승인은 시스템 밖에서 수기(오프라인)로 진행 (컴플라이언스/커스터디 팀이 이메일·대면 등으로 수령·심사).
고라니 시스템은 ORG별 KYC 승인 상태(미승인/승인) 만 관리 — 관리자가 오프라인 심사 결과를 수동 반영. 이 상태가 거래·출금 게이팅 기준.
→ 인앱 서류 업로드 UI·심사 콘솔은 MVP 제외(개발량 감소). 원본 5년 보관은 컴플라이언스 팀이 오프라인 보관. (감사 대비 승인 근거 메모·첨부는 선택.)
G. FDS (이상거래탐지) — [서드파티] (BE 연동)
솔루션 구매 후 연동(요구사항대로). 거래/출금 이벤트 스트림 → FDS 스코어 → Policy Engine 입력.
H. OFAC / KYT (온체인 스크리닝) — [확인 후 결정] (BE 연동)
Chainalysis 또는 Elliptic — 입출금 주소·트랜잭션 제재(OFAC/SDN)·위험 스코어링.
✅ 사내 커스터디 규제 준수 체계에 KYT/제재 스크리닝이 이미 포함되어 있을 가능성 → 우선 사내 체계 범위 확인. 포함 시 그 결과를 Policy Engine 입력으로 재사용. 미포함 시에만 별도 벤더 연동.
I. 홈 대시보드 — [개발] (BE/FE)
관리 자산 총액, 자산 비중(ETH/USDT/USDC) 시각화, 핫/콜드 분포, 최근 거래·승인 현황.
평가금액·자산 비중 산정용 시세는 사내 Price Hub 사용 (외부 시세 API 미사용).
J. 거래 (Trading) — [개발 오케스트레이션] + [서드파티 유동성] (BE/FE)
실시간 견적(RFQ) → 호가 표시 → 사용자 확정 → 체결 → 핫월렛 정산 → 기록.
유동성은 외부 LP/OTC 또는 거래소 계정 [서드파티]. (MVP는 7장 OTC 전략 참고.)
K. 중개 (Brokerage) — [개발] (BE/FE)
회원 기관 간 대량 매매: 매도/매수 의향 등록 보드 → (브로커 보조) 매칭 → 협상 → 체결.
체결 시 ORG 간 지갑 이전 + 승인라인 + Policy Engine + (대상 시) Travel Rule.
L. 로그·감사 — [개발] (BE) ★ISMS 필수
행위로그(사용자 액션), 감사로그(권한·정책·승인 변경), API 로그. 위변조 방지·보존.
M. 관리자 기능 — [개발] (BE/FE)
요청 승인/반려, 상태 변경, 사용자·지갑·거래 조회, ORG 관리, KYC 승인 상태 설정.
N. Travel Rule — [서드파티] (BE 연동) ★VASP 필수
100만원 이상 가상자산 이전 시 송수신인 정보 교환. CODE 또는 VerifyVASP(람다256) 연동.

핵심 원칙: 키·콜드 보관(보관의무)은 사내 커스터디, 노드·시세는 사내(올댓노드·Price Hub) 자산을 그대로 활용. 운영 핫월렛 운용·정책·승인·거래/중개·대시보드는 직접 개발. 제재 스크리닝·트래블룰만 외부.

5. 백엔드 / 프론트엔드 / 컨트랙트 개발 분류
5-1. 백엔드 (BE) — 가장 큰 비중
인증·세션·2FA, RBAC, Policy Engine, 승인 워크플로우.
지갑 추상화: 주소 발급/매핑, 잔액·주소 조회, 입금 감지, 운영 핫월렛 입출금 오케스트레이션 · 핫↔콜드 스윕 트리거 · 핫/콜드 비율 모니터링, 출금 플로우(승인→커스터디 서명→브로드캐스트→컨펌 추적).
거래 엔진(RFQ·주문·체결 기록), 중개 엔진(의향 보드·매칭·정산).
원장/회계 기록(내부 잔액 ↔ 온체인 정합성, 증명서 발급용 데이터).
로그·감사.
연동 어댑터: 사내 커스터디 시스템, 사내 올댓노드(노드/RPC), 사내 Price Hub(시세), KYT(OFAC, 사내 미포함 시), Travel Rule, FDS.
5-2. 프론트엔드 (FE) — 웹 (적응형/Adaptive)
로그인/2FA, ORG·멤버·역할 관리.
홈 대시보드(자산·비중·핫/콜드 차트).
거래 화면(견적→체결), 중개 보드.
승인 대기함(Approver inbox).
관리자 콘솔(요청 통제 + KYC 승인 상태 설정). ※ KYC 서류 업로드·심사 화면은 수기 전제로 MVP 제외.
리포트·증명서 다운로드.
5-3. 컨트랙트 (Contract) — MVP에선 사실상 불필요 ★
취급 자산이 ETH(네이티브) / USDT / USDC(둘 다 이미 배포된 표준 ERC-20)뿐 → 자체 토큰 컨트랙트 개발 불필요.
송금은 표준 ERC-20 transfer 호출 → 커스텀 컨트랙트 개발 불필요.
(옵션·후순위) 온체인 거버넌스가 필요하면 Safe(Gnosis Safe) 멀티시그 — 배포·설정 수준이지 개발이 아님.
결론: MVP의 컨트랙트 개발 공수 ≈ 0. 인력을 BE/FE에 집중.

6. 네트워크 연결 (ETH / USDT / USDC)
6-1. 체인 전략 — 단일 체인으로 단순화
자산을 3종으로 한정했으므로 MVP는 이더리움 메인넷 단일 체인만 지원.
ETH = 네이티브(가스 토큰), USDT·USDC = 이더리움 메인넷 표준 ERC-20. 주소 1개로 3종 모두 수신.
(참고: 트론 USDT 수요가 크지만 체인이 늘어나므로 MVP 제외 → 2차 확장 시 검토.)
6-2. 노드/RPC 접근 — 사내 올댓노드
이더리움 메인넷 노드/RPC는 사내 올댓노드(AllThatNode) 사용 (외부 매니지드 RPC 미사용).
잔액 조회·트랜잭션 브로드캐스트·입금 감지(블록/주소 모니터링)를 올댓노드 기반으로 구성.

6-4. 키관리·서명 · 핫/콜드 (사내 커스터디 활용)
키관리·서명·콜드 보관(보관의무) 은 사내 커스터디. 운영 핫월렛 서명도 커스터디 정책 하에서 처리되는지 확인 필요(핫=운영 한도/정책, 콜드=보관·다중승인·에어갭).
콜드월렛이 보관의무(≥80% / ISMS·특금 ≥70%)를 충족. 고라니는 핫/콜드 비율을 모니터링·가시화하고 스윕을 트리거.
→ 외부 커스터디 솔루션(Fireblocks/BitGo/Cobo/KDAC 등) 도입 불필요.
확인 사항: (a) 핫/콜드 서명 정책, (b) 스윕·보충 API와 소요시간, (c) ERC-20 출금 가스 충전 주체, (d) 지원 자산·체인.

7. OTC를 빠르게 구축하는 방법
요청대로 “우리가 사서 해준다”를 포함해 3가지 모델을 비교합니다.
모델 A — 프린시펄(자기거래) “우리가 사서 판다” ★MVP 권장
고객 주문을 고라니가 외부 거래소/LP에서 직접 체결해 자기 재고로 메우고 스프레드로 수익.
초기엔 수동 OTC 데스크: 고객이 UI로 견적 요청 → 운영자가 외부에서 체결 → 시스템에 가격·수량 입력 → 고객 확정 → 핫월렛 정산.
장점: 매칭엔진·LP 다중연동 없이 가장 빠르게 풀 플로우(견적→체결→정산)를 실구현으로 보여줄 수 있어 ISMS 예비심사에 유리.
필요: 외부 거래소/LP 계정 1~2곳, 스프레드/호가 로직, 재고·노출 관리, VASP 교환업 라이선스.
모델 B — RFQ 중계(에이전시)
외부 OTC 데스크/LP에 견적 요청 → 고객에 전달 → 체결 중계(고라니는 중개 수수료). 재고 리스크 없음.
모델 C — 유동성 API / 프라임브로커 연동
FalconX·Talos·국내 LP 등 API로 자동 RFQ. 가장 “제품다운” 형태지만 구축 시간이 가장 김 → MVP 이후.
권장 로드맵: MVP는 모델 A(수동 프린시펄 데스크)로 빠르게 → 동시에 모델 C용 LP API 1곳 연동 병행 → 검증 후 자동화 확대.

8. 중개(Brokerage) 모듈 MVP 스펙
의향 등록 보드: 회원 기관이 자산/수량/희망가/유효기간으로 매도·매수 의향 등록.
매칭: MVP는 운영자(브로커) 보조 매칭 + 후보 노출. (완전 자동 호가매칭은 후순위.)
체결·정산: 합의 시 ORG 간 이전 → Policy Engine → 승인라인 → (대상 시) Travel Rule.
리포팅·증명서: 체결 내역, 잔고증명, 거래내역 증빙 발급.

9. MVP 범위 / 비범위
In Scope (심사 통과 + 운영 최소선)
인증·2FA · RBAC · Policy Engine · 승인라인 · 수탁지갑(운영 핫월렛 + 콜드 보관(커스터디), 핫/콜드 비율 유지) · KYC 상태 게이팅(서류는 수기/오프라인) · OFAC/KYT(사내 확인 후) · Travel Rule · FDS 연동 · 홈 대시보드(사내 Price Hub 시세) · 거래(수동 프린시펄) · 중개(의향보드+보조매칭) · 로그/감사 · 관리자 기능.
Out of Scope (2차)
멀티체인(트론 등) · 완전 자동 매칭엔진 · 자동 LP 다중 라우팅 · 자동 KYC(벤더) · 온체인 거버넌스 컨트랙트 · 모바일 앱 · 스테이킹/수익상품.

10. 권장 우선순위 (인력 6명 가정)
기반(必先): 인증·2FA·RBAC·ORG 가입 + 로그/감사 골격.
커스터디 연동 + 지갑 레이어: 인터페이스 합의(주소 발급·서명·콜드 스윕/보충). 운영 핫월렛 입출금·입금 감지·핫/콜드 비율 모니터링 우선. 노드는 사내 올댓노드.
Policy Engine + 승인라인: 거래·출금 플로우의 중심.
거래(수동 프린시펄 데스크) + 대시보드(Price Hub): 데모 가능한 가치 흐름.
컴플라이언스 연동: OFAC/KYT, Travel Rule, FDS.
중개 보드 + 리포팅/증명서.
컨트랙트 개발 인력은 불필요 → 백엔드·인프라·컴플라이언스 연동에 재배치 권장.
