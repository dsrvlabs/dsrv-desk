# 37. 커스터디팀 연동 요청문 — 기관 상태 조회 · 거래 위험 차단 통지 · 웹훅 실패 대비 (2026-09-07 최종)

> 성격: 커스터디팀에 보내는 요청 문안(기획 산출물 · 근거 아님). 결정 정본 = knowledge/09 §0 2026-09-07(21)·(22). 회의 설명자료 = drafts/36. 커스터디 AS-IS 사양 = reference/custody/01(2026-07-01 기준 · 현행 여부 재확인 필요).
> 초안(같은 날 오전)에 있던 '상태 변경 웹훅' · '차단 사유 코드' · '되묻는 조회 API'는 사용자가 제외했다. 아래가 최종이다.

## 0. 보내는 문안 (그대로 붙여 쓰는 버전)

커스터디팀에 요청드리는 연동 사항은 3건입니다.

1. **기관 KYC 상태**
   1-1. 조회 API — 저희 서비스가 customerNo로 요청하면 그 기관의 현재 상태 코드를 돌려주는 API. 로그인·거래 요청·수락·승인 시점마다 호출합니다.
   1-2. 상태 코드는 Custody Admin의 customerStatusCd(01 신규 / 02 활성 / 03 휴면 / 04 거래중지 / 05 거래해지 / 06 거래거절)를 그대로 쓰겠습니다.

2. **거래 위험 판정(AML) — 문제가 있을 때만 통지**
   2-1. 집행 전 심사(블랙리스트·KYT 등)에서 해당 거래를 진행할 수 없다고 판정되면 웹훅으로 즉시 알려주시면 됩니다.
   2-2. 내용은 거래 건 번호(EXC-… / BRK-…)만 있으면 됩니다. 사유는 받지 않겠습니다.

3. **웹훅 실패 대비**
   3-1. 웹훅 전송 실패 시 재시도(횟수·간격은 커스터디 정책에 따름).
   3-2. 재시도까지 실패하면 슬랙으로 한 번 더 알려주시는 것으로 내부 정책서에는 쓰겠습니다. 이 부분은 신경 안 쓰셔도 됩니다.

## 2. 내부 정책(커스터디 요청 항목 아님)

- 웹훅 재시도까지 실패하면 커스터디가 슬랙으로 알린다 → 관리자가 ADM-02 ② 집행 대기의 해당 행에 [이전 중지]로 수동 처리한다. 되묻는 조회 API는 두지 않는다.
- 미수신 행은 집행 대기에 남는다(보류 만료 없음 · 09 §0 (17)⑩). 슬랙 통보가 유일한 보정 경로이므로 운영 정책서에 절차·담당을 적는다.

## 3. 요청하지 않는 것

- 상태 변경 웹훅 — 관문마다 조회하므로 다음 관문에서 반영된다(사용자 결정).
- 차단 사유 코드·단계 정보 — 고객에게는 "이슈로 진행 불가"만 전달한다. 반환 필요 여부는 우리 장부의 txHash 입력 여부로 판단한다.
- 성공 집행 통지 — txHash 수동 입력 + 온체인 4항목 대사로 닫힌다(ADM-02 ② 집행 대기).
- 사고 유형·기간 — 기관 상태 코드로만 받는다(09 §0 (21)⑧).
- 잔고·AML 보고 데이터·KYT 심사 로직 — 각각 온체인 직접 조회 · 커스터디 자체 등록 · 커스터디 소유(09 §0 (21)③④⑩).

## 4. 남은 확인 사항(회의에서)

- 압류·동결 등 지갑 단위 사고 등록이 customerStatusCd에 어떻게 반영되는지(04 거래중지로 오는지, 별도 값인지).
- 05 거래해지·06 거래거절 기관의 로그인 허용 여부(현재 안 = 조회만 허용).
- Custody Admin이 폐쇄망이라면 외부 API·웹훅을 어떤 경로로 열 수 있는지, 신설 가능한 팀·일정(drafts/36 Q1·Q2).
- 위 AS-IS 사양(2026-07-01 Notion)이 현행과 같은지.
