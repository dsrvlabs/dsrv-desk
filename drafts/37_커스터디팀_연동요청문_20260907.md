# 37. 커스터디팀 연동 요청문 — 기관 상태 · 거래 위험 판정 · 웹훅 실패 대비 (2026-09-07)

> 성격: 커스터디팀에 보내는 요청 문안(기획 산출물 · 근거 아님). 결정 정본 = knowledge/09 §0 2026-09-07(21)·(22). 회의 설명자료 = drafts/36. 커스터디 AS-IS 사양 = reference/custody/01(2026-07-01 기준 · 현행 여부 재확인 필요).

## 0. 보내는 문안 (그대로 붙여 쓰는 버전)

커스터디팀에 요청드리는 연동 사항은 3건입니다.

1. **기관 KYC 상태**
   1-1. 조회 API — 저희 서비스가 customerNo로 요청하면 그 기관의 현재 상태 코드를 돌려주는 API. 저희는 로그인·거래 요청·수락·승인 시점마다 호출합니다.
   1-2. 상태 변경 웹훅 — 기관 상태가 `02 활성`에서 다른 값으로 바뀌는 순간 저희 쪽으로 push. 대기 중인 거래를 바로 거절하기 위해 필요합니다.
   1-3. 상태 코드는 Custody Admin의 customerStatusCd(01 신규 / 02 활성 / 03 휴면 / 04 거래중지 / 05 거래해지 / 06 거래거절)를 그대로 쓰겠습니다. 저희 화면·문서도 이 코드에 맞춰 바꿉니다.

2. **거래 위험 판정(AML) — 문제가 있을 때만 통지**
   2-1. 집행 전 심사(블랙리스트·KYT 등)에서 해당 거래를 진행할 수 없다고 판정되면 웹훅으로 즉시 알려주시면 됩니다.
   2-2. 내용은 거래 건 번호(EXC-… / BRK-…)와 사유 코드만 있으면 됩니다. 어느 단계(예치·인도 등)인지는 저희가 알 필요 없습니다.
   2-3. 정상 집행은 지금처럼 어드민에 txHash를 입력해 주시면 저희가 온체인에서 확인해 완료 처리합니다. 성공 통지는 필요 없습니다.

3. **웹훅 실패 대비**
   3-1. 웹훅 전송 실패 시 재시도(횟수·간격은 커스터디 정책에 따름).
   3-2. 저희가 되물을 수 있는 조회 — 기관 상태는 1-1을 재사용, 거래 위험은 "미완료 건의 판정 결과 조회" 1개.
   3-3. 재시도까지 실패하면 운영 채널(메일·메신저)로 한 번 더 알려주시기를 요청드립니다.

확인이 필요한 사항은 아래와 같습니다.

- 압류·동결 등 지갑 단위 사고 등록이 기관 상태 코드에 어떻게 반영되는지(04 거래중지로 내려오는지, 별도 값인지).
- 거래 위험 판정 3분류(적정 / 보완 / 부적정) 중 '보완'도 웹훅으로 보내주실지, 보완 시 고객 증빙 요청은 현행처럼 커스터디가 진행하는지.
- Custody Admin이 폐쇄망이라면 외부 API·웹훅을 어떤 경로로 열 수 있는지, 신설 가능한 팀·일정.
- 위 AS-IS 사양(2026-07-01 Notion)이 현행과 같은지.

## 2. 요청하지 않는 것

- 성공 집행 통지 — txHash 수동 입력 + 온체인 4항목 대사로 닫힘(ADM-02 ② 집행 대기).
- 단계(입고·출고·예치·인도) 정보 — 반환 필요 여부는 우리 장부의 txHash 입력 여부로 판단.
- 사고 유형·기간 — 기관 상태 코드로만 받는다(09 §0 (21)⑧).
- 잔고·AML 보고 데이터·KYT 심사 로직 — 각각 온체인 직접 조회 · 커스터디 자체 등록 · 커스터디 소유(09 §0 (21)③④⑩).

## 3. 이 요청이 확정되면 바뀌는 우리 쪽 산출물 (후속)

- 상태 라벨 5종 → customerStatusCd 6종: states · notation · dash-01 · exc-01 · exc-02 · adm-02 · adm-03 · brk-04 · onb-00 · DB스키마 20260902 · drafts/34 · drafts/36(P2·P4·P6·D1·D4 확정 표기).
- ADM-02 ② 집행 대기의 '위험 판정 칸'(수동 입력) → 웹훅 수신 결과 표시로 전환.
- ADM-03 [상태 변경 ▾] 처리 — 삭제 또는 웹훅 미수신 시 수동 보정용으로만 유지. **사용자 결정 필요**(09 §0 (22)② [확인필요]).
