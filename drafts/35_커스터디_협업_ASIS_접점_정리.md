## 0. 한 줄 결론

- 교환·중개 시스템은 **고객·KYC·지갑·콜드 서명·AML 솔루션 보고를 소유하지 않는다.** 전부 커스터디팀(Custody Admin·월렛룸)과 컴플라이언스팀(AML 담당 부서)의 기존 체계다. 우리 시스템은 **주문·상태·승인·집행 지시·대사·CSV**만 갖는다. [추론 — 09 §0 2026-09-04(17) 결정과 이번 자료가 일치]
- 커스터디와 만나는 지점은 **8곳**(§2). 그중 회의에서 정해야 하는 것은 **집행 지시서가 커스터디 품의 체계에 어떻게 들어가는지**(§2-E), **내부 이전을 AML 솔루션에 어떻게 보고하는지**(§2-F), **고객 상태·잔고·AML 결과값을 어떤 경로로 받는지**(§2-A·D·G) 세 가지다.
- 이번 자료로 **우리 전제와 상충하는 항목 14건**(§6)이 나왔다. 약관 clean판 3건(장부 대체·등록 지갑 주소·수수료 별도 정산)과 K&C 샘플 전제(실시간 복수거래소 가중평균)는 회의 전에 방향만 정해 두면 된다.

### 1-3. 업무 흐름 [사실 — 운영매뉴얼 2장]

**온보딩** 문의(Portal·홈페이지·유선) → 온보딩 대장 기록 → 서류 발송(대표자/대리인 세트 + CARF용 재무제표) → AML 진위 확인 → 계약 날인 → Portal 계정 등록 → **Custody 어드민 고객 등록 → KYC 승인·AML 확인 → 수탁 상품 생성** → 'Custody 작업신청 요청서' 품의(영업일 3일 내외) → 월렛룸 지갑 생성 + 소액 입출금 테스트 → 신규지갑생성확인서(날인) → '작업완료보고' 품의 → '가상자산 위탁 신청(보관·관리) 이용자명부' 기록.

**입금** 고객 '지갑 입금 신청서'(영업일 3일 전 · 취소 1일 전 · 테스트 입금 선행 · 1일 1회 이하) → '입출금 요청 관리 대장' → 화이트리스트 미등록 시 등록 품의 → **Custody팀 + AML 부서 공동 모니터링** → 잔고 반영 → 잔고확인서(날인) → '위수탁 결과보고서' 품의 → 이용자명부 최신화. 고지 없는 입금은 AML 검토(적정 → 변경 계약 후 반영 / 보완 → 출금 일시 제한 / 부적정 → 원천 반환·STR·동결).

**출금** 예상 가스비와 함께 '지갑 출금 신청서' → 품의 4종('출금 가스비 요청 신청서'·'출금 작업계획서'·'화이트리스트 등록 신청서'·'작업 신청 요청서', 영업일 3일 내외) → 화이트리스트·출금 사전 검증 이상 내역을 AML 부서에 공유 → AML 검토(적정 → **최종 승인권자 결재 → 실행** / 보완 → '대기' + 증빙 요청 / 부적정 → 즉시 거부·STR) → 월렛룸 작업 → Custody 어드민 거래 내역 확인·자산 반영 → 잔고확인서 → 작업완료보고 → 이용자명부.

**거래 보류 사유**(매뉴얼 4.4) 압류·동결 통보 / 미신고 VASP / VASP 위험평가 미이행 / 개인지갑 명의 불일치 / 제재 대상 / KYC 미이행 / 오입금 / 화이트리스트 미등록 / 수량 부정합 / 송금인 정보 부재 / VASP 불일치. **차단 근거** = Custody 약관 제16조(이용자보호법 §11), 이용 제한 = 제17조.

## 3. 백엔드 팀 안내 (회의에서 전달할 원칙)

### 3-1. 소유 경계 [추론 — 09 §0 (17) + 이번 자료]

| 우리 시스템이 갖는 것 | 갖지 않는 것(커스터디·AML 기존 체계) |
|---|---|
| 기관 계정(로그인·2FA)·권한, 교환 요청·게시·신청·협의·확정 레코드, ADM-02 4섹션 상태 전이, 승인·거절·보류 기록, 집행 지시 행·명세 Excel, 온체인 대사(3면 중 '장부'·'온체인'), CSV 6종, 시세 소스·스프레드·한도 설정(ADM-03) | 고객 마스터·KYC·관련인 정보(실명번호 등 개인정보), 지갑 생성·키·콜드 서명, 화이트리스트, 외부 입출금, AML 솔루션 호출·STR, 트래블룰, 잔고확인서·이용자명부 |

### 3-2. 개발 원칙 (안내 문안)

1. **고객 개인정보를 저장하지 않는다.** 기관 식별자(customerNo)·법인명·기관 상태만 보유. 대표자·대리인·실소유자 정보는 Custody Admin 영역이며 우리 DB에 컬럼을 두지 않는다. (AML API가 실명번호를 복호화 전송하는 구간은 Custody Admin ↔ 폐쇄망 솔루션 사이의 일)
2. **콜드 서명·온체인 전송은 우리 코드가 하지 않는다.** 우리는 집행 지시 행을 만들고, 결과(txHash·실 가스비·완료 시각)를 받아 대사한다. 09-04(17)④ "콜드 서명 장애는 우리 알림 유형에 없다" 유지.
3. **AML 솔루션을 직접 호출하지 않는 것을 기본 가정으로 둔다.** 솔루션은 운영망(폐쇄망) 내부다. 보고에 필요한 데이터(seq·일시·customerNo·지갑 주소·유형·자산·수량·KRW 환산·txHash·상대 주소)를 **우리가 생성해 넘기고**, 호출 주체·경로(Admin 경유/파일/API)는 §2-F 결정 후 확정. → **연동 계층을 어댑터로 분리**해 결정이 늦어도 코어 개발이 멈추지 않게 한다.
4. **커스터디→우리 수신 데이터는 5종으로 고정하고 스키마를 먼저 합의한다.** ① 기관 상태(활성/거래중지/거래해지/동결 + 시작·종료) ② 자산별 수탁 잔고 ③ AML 결과값(KYC 결과·재이행 진행 중·WLF 적중·고위험) ④ 집행 결과(행 ID·txHash·실 가스비·완료 시각·서명자 ID) ⑤ 콜드 기록(3면 대사용, 형식 [확인필요]). 수신 방식은 미결이므로 **폴링·수동 업로드·API 어느 쪽이든 동작하는 입력 인터페이스**로 설계.
5. **KRW 환산은 두 곳에서 쓰인다.** 우리 한도 판정(ADM-03 시세 소스)과 AML 보고 krwAmount(현행 커스터디는 "회사가 표시하는 기준가액", AML 매뉴얼 3.7.1②). 소스가 다르면 값이 갈린다 → 같은 소스를 쓰거나 보고 시 어느 값을 쓰는지 §2-F에서 함께 결정.
6. **바로 시작할 수 있는 것**: 기관 계정·화면·주문/게시/신청 상태 머신·ADM-02 4섹션·시세 소스 어댑터·한도 판정·CSV. **결정을 기다려야 하는 것**: 커스터디 연동 5종 수신 스키마, AML 보고 데이터 생성 규칙, 지시서 포맷(커스터디 품의 서식과의 매핑), 4묶음 지갑 주소.

### 3-3. 백엔드가 회의에서 물어야 할 것

- Custody Admin의 데이터 모델(고객·지갑·거래·상품)과 외부 연동 가능 여부(API 존재? 폐쇄망 안에 있는지?)
- '자산 구분 CUSTOMER / DUST_TEST 승인'이 무엇인지(입금 트랜잭션 분류 절차로 추정 [추론]) — 우리 집행 결과가 이 절차를 타는지
- 콜드 기록(3면 대사의 3번째 면)의 실제 형식(엑셀? Admin 테이블?)
